# POLARIS ML Engine

Working implementation of the 4 ML components recommended for POLARIS:

| # | Component | Problem type | Model |
|---|---|---|---|
| 1 | Weather / Blizzard Risk | Classification | XGBoost Classifier |
| 2 | Fuel & Inventory Forecasting | Regression / time series | XGBoost Regressor |
| 3 | Cold-Chain Anomaly Detection | Unsupervised anomaly detection | Isolation Forest (on engineered trend features) |
| 4 | SAR Risk + Asset Ranking | Classification + weighted scoring | XGBoost Classifier + rule-based ranker |

All four are trained on **synthetic data** generated by `data_gen.py`, since no
real station telemetry was provided. The synthetic generators encode the same
causal relationships described in the spec (colder + windier + lower pressure
→ higher blizzard risk; more personnel + load + blizzard → higher fuel burn;
etc.), so the models learn realistic patterns and are ready to demo out of the
box. **Swap in real telemetry** by replacing the CSVs in `data/` with real
data using the same column names — no other code changes needed.

## Project structure

```
polaris_ml/
├── data_gen.py              # synthetic data generators (replace with real data)
├── data/                    # generated CSVs land here
├── models/
│   ├── blizzard_risk.py     # ML #1
│   ├── fuel_forecast.py     # ML #2
│   ├── coldchain_anomaly.py # ML #3
│   └── sar_risk.py          # ML #4 (risk model + asset ranker)
├── api.py                   # FastAPI service exposing all 4 models
├── dashboard.html           # standalone demo UI (talks to the API)
└── requirements.txt
```

## Setup

```bash
pip install -r requirements.txt
```

## Run the API

```bash
python api.py
# or: uvicorn api:app --reload --port 8000
```

On first startup it trains all 4 models on synthetic data (a few seconds) and
caches them to `models/*.pkl`. Interactive API docs:
`http://localhost:8000/docs`.

## Try it

Open `dashboard.html` directly in a browser (no build step) while the API is
running — it's a single static file that calls `http://localhost:8000` by
default (editable in the top bar). Each of the 5 panels mirrors an example
from the design doc, pre-filled with the same numbers, so you can demo the
exact "Snowcat B wins / Field-Team-07 at CRITICAL / cold-chain breach in
~18 min" scenarios live.

Or hit the API directly:

```bash
curl -X POST http://localhost:8000/predict/weather-risk \
  -H "Content-Type: application/json" \
  -d '{
    "station":"Bharati","temperature_c":-38,"wind_speed_kmh":95,
    "wind_gust_kmh":130,"pressure_hpa":955,"pressure_change_3h":-6,
    "visibility_m":250,"humidity_pct":88,"wind_chill_c":-55
  }'
```

## Retraining individual models

Each model file is runnable standalone and prints metrics:

```bash
python models/blizzard_risk.py       # AUC ~0.96
python models/fuel_forecast.py       # MAE ~220 L/day, R2 ~0.6
python models/coldchain_anomaly.py   # trains + scores an example warming trend
python models/sar_risk.py            # AUC ~0.78, prints incident risk + asset ranking
```

## Wiring this into POLARIS

Each endpoint returns the same fields shown in the design doc's example
outputs, so they drop straight into the dashboard/GIS layer:

- `POST /predict/weather-risk` → blizzard probability, visibility/wind risk, confidence
- `POST /predict/fuel-forecast` → burn rate, day-7/14/21/30 stock projection, exhaustion day, risk
- `POST /predict/coldchain-anomaly` → anomaly flag/score, estimated steps to threshold breach
- `POST /predict/sar-risk` → response risk %, estimated response time, risk level
- `POST /predict/sar-asset-ranking` → ranked list of assets by suitability score

To build the decision chain from the doc (blizzard → +fuel burn → autonomy
drop → resupply recommendation → contingency plan), call `/predict/weather-risk`
first, feed `blizzard_probability_pct` into the `blizzard_flag`/conditions of
`/predict/fuel-forecast`, and branch your logistics module on the returned
`risk` field.

## Notes / limitations

- Accuracy numbers (AUC ~0.96 for blizzard, ~0.78 for SAR, R2 ~0.6 for fuel)
  reflect the synthetic data's signal-to-noise ratio, not real-world
  performance — retrain on real telemetry before using metrics in a report.
- The cold-chain model is unsupervised (Isolation Forest on rolling
  mean/std/slope features), so it needs no labeled anomaly examples — a good
  fit given real breach events are rare.
- The asset ranker is a transparent weighted-score function rather than a
  learned model, since suitability weights (distance/fuel/weather/availability)
  are better defended as explicit, auditable business rules for a rescue
  decision than a black-box score.
